# notice-route: design

Status: designed 2026-11-17 against architecture v1.24, revised after review. The normative rules are in [interface.md](interface.md); this document records why, and how the tool is built. It links to interface headings and does not restate their tables.

## Role and layer

Layer 2 (composite). Routes notifications to channel notifiers by source, labels, level and time, with quiet hours, deferral, dedup, a per-destination rate cap, retries and a history. It works fully standalone: it needs only a command that accepts `send --stdin-json`, and the three notifiers we ship are the natural targets. It has no upward awareness: a producer reaches it through a hook line in the producer's own config, and nothing in the router knows who that producer is beyond the `tool` name in the payload.

## Uses

| Dependency | Binding | Notes |
|---|---|---|
| slack-notice, ha-notice, wsl-notice | B (configurable command) | Each destination names a command; the call shape is fixed (`send --stdin-json --json --actor auto:notice-route [--dedupe-key=<hex>]`). A `kind` selects the retry rules. See [Destinations](interface.md#destinations) and [Calling the notifiers](interface.md#calling-the-notifiers). |
| any other notifier | B, `generic` kind | Works when it accepts the call's words and reads the notification JSON from stdin; otherwise a wrapper script. No adapter code is shipped. |
| a time-zone database | system | `zoneinfo` from the standard library with the system database. |

The architecture entry for this tool said "binding C (adapters)" and also fixed the call shape, which is binding B. The call shape wins (D-6), and the architecture entry is corrected in v1.24. No other tool is a dependency: pr-watch, review-watch, ticket-work, agent-spawn and the rest reach the router only through hooks wired in their own configs.

## Decisions

| ID | Decision | Rationale | Interface |
|---|---|---|---|
| D-1 | Two input shapes told apart by keys, no mode flag; `payload_unrecognized` and `source_mismatch` refusals. | One documented hook line; a script cannot rename another tool's events. A rule without `message` passes a notice's own text through. | [Input shapes](interface.md#input-shapes) |
| D-2 | First matching rule wins; a rule can fan out to up to 8 destinations or `drop`. | One rule explains a routing; adding a rule cannot silently duplicate sends. | [Rules](interface.md#rules) |
| D-3 | The rule decides the level; the notice's own level is only a fallback; no `--level` flag. | A script cannot claim `error` to bypass quiet hours on a rule that fixes the level. A rule that can match a hook payload must set `level`. | [Levels](interface.md#levels) |
| D-4 | Templates are a single-pass `{{field}}` substitution. A payload value goes into a title only when it is plain (a number, a boolean, or a word-like string of letters, digits and `._/#-`); other text reaches only a message, through `include_text`, for payloads with `reads_third_party: false` and `tainted: false`. | The value is judged, not its field name, so a new free-text field fails closed without a list that tracks every producer; "what the agent asked" stays possible. | [Untrusted text](interface.md#untrusted-text), [Templates](interface.md#templates) |
| D-5 | Links come only from `links` tables and fixed payload ids. | A producer cannot aim the tap target, and a rule's link is one derived token or a literal URL. | [Links](interface.md#links) |
| D-6 | A destination is a command (binding B) with `kind`, `floor`, `quiet`, `max_per_hour`, `env`. | The call shape is fixed; adapters would track each notifier's changes. | [Destinations](interface.md#destinations) |
| D-7 | Named quiet windows referenced per destination; `timezone` required; wall-clock minute-of-day rule; only `error` bypasses. | A phone should be quiet while a desktop toast is harmless; spike A. | [Quiet hours](interface.md#quiet-hours) |
| D-8 | Notifications deferred for quiet hours or the cap are `held` queue rows, folded into one digest per destination titled `N held notifications`; at most 100 unclaimed queue rows per destination; rows 24 hours old or more expire. | Fifteen buzzes at 07:00 defeat quiet hours. Lines name the event (title and message head) and put the highest level first. | [Deferral and digest](interface.md#deferral-and-digest) |
| D-9 | Two dedup checks per destination: redelivery by source, hook, `event_id` and the repeat digest, and a fixed-window repeat check keyed on the notification as it would be sent (level included); its digest is passed as `--dedupe-key=<hex>`. | Two notifications that look the same are one; any field that shows makes them two, without a list of producer fields. A sliding window suppresses a steady repeater forever. Event ids are compared per source and hook, because producers number them independently. Records live while their delivery is pending, sent or unknown, so an undelivered notification never mutes its own redelivery. The digest stops a forged future id from muting the real event. | [Dedup](interface.md#dedup) |
| D-10 | Every notification a destination will receive later is a queue row (`held` or `single`) claimed by the call that sends it, and a send-now decision is a `single` row written before its call; retries go through the queue and `flush` with a fixed schedule; a possibly-sent outcome is never retried (ha-notice's both-true excepted). | A hook-run `send` must end quickly; retrying a possibly-sent Slack message duplicates it. A crash during a call is the one case that resends (at least once). A notifier ended by a signal it did not report is treated as possibly sent. | [Retries and outcomes](interface.md#retries-and-outcomes) |
| D-11 | Exit 0 means the router took responsibility for every destination; 12 means a definite failure or unknown outcome; 22 means nothing to do. | Scripts can tell a failure from quiet hours or dedup. | [Exit codes](interface.md#exit-codes) |
| D-12 | History keeps the rendered title of a templated rule (literal text and plain values only) and hashes; message text is deleted with its queue row; no `audit.jsonl`. | Free text never rests on disk after delivery; stored ids and labels are plain or label-grammar values. | [Files](interface.md#files), [Log](interface.md#log) |
| D-13 | Config and state are found only from the password-database home; owned-by-user and no group or world write; no per-repo or environment layer; `--config` only on commands that run nothing. | The config selects commands that run with credentials in their environment. `--config` is accepted only by commands that run nothing, and a sandboxed session is never allowed `send`, because `send` writes the state directory that `flush` delivers from. | [Environment variables](interface.md#environment-variables), [Config](interface.md#config) |
| D-14 | One hook, `post-fail`, run by `flush`, with a recursion guard on `NOTICE_ROUTE_HOOK`; surfaced failures are also routed through the rules as source `notice-route`. | A way to learn a channel is down without a loop, with quiet hours, floors and credentials applied like any other notification. Surfacing only writes a row; `flush` routes the alert and runs the hooks, so `send`'s time bound never includes a hook. | [Hooks](interface.md#hooks) |
| D-15 | Eight commands; no `queue` or `destination` management in 0.x; `test` is explicit, never sends and takes `send`'s input flags. | Each command has one job; management is state reachable by config and `history`. | [Commands](interface.md#commands) |
| D-16 | Process model: parallel across destinations, serialized per destination by `flock`, own process group, bounded output, monotonic deadline, group kill. | Spike B. | [Calling the notifiers](interface.md#calling-the-notifiers) |
| D-17 | A per-destination counter of calls claimed per UTC hour, kept separately for `error` and for the other levels; a notification over the cap is held for the next hour and folded into a digest. | Dedup stops repeats, not a flood of distinct events. A flood of non-errors cannot delay an `error`, and eviction drops the lowest level first. A digest is never held by the cap, so held rows cannot starve. | [Rate limit](interface.md#rate-limit) |
| D-18 | No built-in rules or destinations; `config.example.yaml` plus the drop-in are a complete worked config. | A built-in rule would silently change who is pinged when a producer's enum list changes. `validate` knows no producer; the example is checked in CI. | [Config](interface.md#config) |

## Calls made by the author

Decisions the user did not see as choices, made while writing and open to correction:

- C-1: the whole-call budget of the approved model bounds only the lock wait (a started call runs to its deadline); `lock_wait` defaults to 2s, a `send` makes at most one call per destination, and the worst case is 29 s with defaults, counted from the end of input, under the hooks' 30 s default. `validate` prints the figure; the bound excludes input reading and every hook (hooks run from `flush`).
- C-2: a destination's `timeout` is at least the notifier's own; the router cannot read the notifier's value.
- C-3: input limits for the strict reader (1 MiB, depth 16) and label grammar (producer-compatible, up to 64 payload labels read and 32 `--label`).
- C-4: the retry schedule (1 m, 5 m, 30 m, 2 h counted from the end of the previous call; 5 attempts, 3 for wsl-notice, its caller contract), digest size (10 lines), the 24 hour expiry; `lock_busy` counts no attempt and is due again after 60 s; after a retryable, `failed` or `unknown` result `flush` stops calling that destination for the run (its other due rows wait for the next run); one 100-row cap covers the unclaimed `held` and `single` rows; immediate retries go through the queue and count as attempts.
- C-5: the cap counts calls claimed (failures too) in the current UTC hour; a digest counts in its highest class and is never held.
- C-7: `post-fail` is best-effort, at most once, run by `flush`, with no outbox in 0.x; expiry, overflow, the cap and a missing credential are surfaced too.
- C-8: a label on a payload that does not fit the grammar is ignored and counted, not refused.
- C-9: exit 20 for payload faults only; `config_unsafe` and bad config are exit 2.
- C-10: pass-through rules require `level_min`, and messages are cut at 4000 characters.
- C-11: a `send` or `flush` that lacks a destination's credential never calls it: `send` queues the notification as a single row due now, `flush` leaves the rows and surfaces `env_missing`; an empty value counts as unset.
- C-13: every call claims its rows and a crash resends (at least once).
- C-14: drop-ins append `rules` and `hooks.post-fail`, merge destination, window and link entries by name, and refuse anything defined twice.
- C-15: the digest title is `N held notifications`.
- C-16: the row caps are 100000 per table, enforced on insert; retention settings are at least 1 day.
- C-17: input from stdin must be complete within 5 seconds of the start of the command, and a lone surrogate is replaced, not refused.
- C-18: a top-level `enabled` key disables the router.
- C-19: a rule that can match a hook payload must set `level`; a rule that does not is a load error, not a warning.
- C-20: `test` takes `send`'s input flags instead of a separate `--input` flag.
- C-21: every call claims its rows and `lock_busy` counts no attempt.
- C-22: the per-destination health that `validate` shows is `surfaced_today`.
- C-23: the row kinds `held` and `single` and the cap on unclaimed rows.
- C-24: the lifetime of the dedup and event-id records: pending, sent or unknown.
- C-25: alerts skip the redelivery check, and row ids are never reused.
- C-26: the outcome table in precedence order, with a code for every row.
- C-27: refusal retries (link, keyword) count as attempts.
- C-28: a digest is never held by the cap.
- C-29: hooks and alerts run from `flush`; `send` runs none.
- C-30: surfacing periods (queue events hourly, other codes daily) and the limit of 8 codes.
- C-31: the alert payload fields `notification_source` and `notification_level`.
- C-32: `send`'s 0.5 s busy timeouts, two transactions.
- C-33: global row caps on insert and at most 16 stored labels.
- C-34: the plain grammar `[A-Za-z0-9][A-Za-z0-9._/#-]{0,255}`.
- C-35: one sanitizing routine for every rendered title and message.
- C-36: drop-ins merge map entries by name.
- C-37: the `flush` heartbeat read by `validate` and `send`, written only by a full run (no `--dry-run`, no `--destination`), with a record of whether the run skipped a destination for a missing credential.
- C-38: the last fixes narrow rules and add none: the cron block starts at a line that begins `# notice-route managed v`, `send`'s advisory needs a queued row, a wrapper must `exec` the notifier and exit 128+N with output is `unknown`, the hook environment is an allowlist like every child's, and `flush` stops calling a destination after `failed` or `unknown`.
- C-39: config loading (#6): the strict loader keeps PyYAML's scanner and parser (the one runtime dependency; C-42 drops `pydantic`) and replaces its resolvers and constructors: only `true` and `false` are booleans, only decimal integers and decimal floats are numbers, and `null`, `Null`, `NULL`, `~` and the empty value are null, so `yes`, `on`, `True`, `010`, `1e3`, `.inf` and dates stay strings. It refuses anchors, aliases (at the first one met, so nothing expands), explicit tags, merge keys (`<<`), duplicate keys, keys that are not strings, lone surrogates and NUL in a string, more than one document, a null document (only an empty or comment-only file is an empty config) and nesting deeper than 16 (the reader's depth, C-3). The YAML error text quotes the file, so it is never kept (not as `__cause__` or `__context__`).
- C-40: `details.key` for config errors: a known key path, an entry name under `destinations`, `quiet_hours`, `links.hosts` or `links.tickets` when it is plain (`[A-Za-z0-9][A-Za-z0-9._-]{0,63}`), `?` for any other key (an unknown key may be a secret pasted as a key; nothing after a `?` is shown), `rules.<index>.name` for a rule name defined twice, `home`, `--config`, `.` for the config directory, `config.d`, and a file path relative to the config directory (`config.yaml`, `config.d/<name>` with every character outside `[A-Za-z0-9._-]` shown as `?`, so two distinct names can show the same key). A `--config` file's own problems are keyed `--config`.
- C-41: the config directory and `config.d` are opened with `O_NOFOLLOW`, so a symlinked directory (a dotfile manager's link) is `config_unsafe`, like a symlinked file; group or world read access is fine, write access is not. A missing `--config` file is `config_invalid` (key `--config`), not `unconfigured`: the user named it. A missing `config.yaml` is `unconfigured` even when `config.d` has files (drop-ins alone configure nothing, and are not read). Drop-ins are the visible `*.yaml` names in `config.d` (not `.yml`, not hidden, not backups), in code point order; a rule name defined twice is refused also within one file; a `null` where `rules`, `hooks.post-fail`, `destinations`, `quiet_hours`, `links.hosts` or `links.tickets` belongs is `config_invalid`; maps merge key by key, and a leaf defined in two files is `config_invalid` (so `retention.history` and `retention.event_ids` may sit in different files). Only the last component of a directory path is `config_unsafe` when it is a symlink or not a directory; a non-directory earlier on the way is a missing directory (`unconfigured` for the home location, `config_invalid` key `--config` for `--config`), and a `--config` whose last segment is empty, `.` or `..` is `config_invalid`. The reader limits are 256 KiB per file, 1 MiB for all files together (conservative, like the 1 MiB reader limit of C-3; the file whose read crosses it is `config_invalid`), 256 drop-ins and 4096 directory entries of any name in `config.d`; an integer or float of more than 20 characters (sign excluded) is `config_invalid`, and only mappings and sequences count toward the depth limit of 16.
- C-42: config validation (#7) is a hand-written validator in `validate.py` that builds frozen dataclasses (`Config`, `Destination`, `QuietWindow`, `Links`, `Rule`, `Match`, `Hook`), not `pydantic`: its error text quotes values and its error locations name unknown keys, both of which C-40 forbids, and a second runtime dependency would buy only the type checks written here. `load_config` still returns the raw merged mapping; `validate_config(data, gateway)` and `load_valid_config` build the typed config, so the loader's tests keep their small fixtures. The key of a problem is its path (`rules.<index>.<key>`, `destinations.<name>.<key>`); a problem inside a list, a `where` map or a `labels` list is keyed by the list or map, never by an element, and a missing required key is keyed by that key (a pass-through rule without `level_min` by `rules.<index>.match.level_min`). Time zones load through `Gateway.load_zone`: only the system database directories, the file read and parsed from memory, so `PYTHONTZPATH` and `zoneinfo.TZPATH` play no part. Choices where the interface is silent, all the narrower reading: a pass-through rule may carry only a literal `link` (the tokens need a payload, which a notice has not); a `post-fail` hook's `cmd` is 1 to 4096 characters and its `timeout` is 1s to 1h; a destination's `env` has at most 4096 entries (spec clarifications, also in `docs/interface.md` and `schemas/config.json`); `retention.*` is at most 100 years; `labels`, `notify`, `env`, `days` and `include_text` list entries must be unique and `labels` and `include_text` non-empty when present (as `schemas/config.json` says); a `cmd[0]` is `/` plus at least one character.
- C-43: input reading (#8) is `payload.py`, one strict reader (`parse_json_object`) that the notifier-output parser reuses; the gateway reads (`read_stdin` with an absolute monotonic deadline of start plus 5 s, `read_input_file` that follows symlinks and checks the opened descriptor, `stdin_is_tty`, `env_present`). Choices where the interface is silent, all the narrower reading: a lone surrogate in a key is replaced before the duplicate check, so keys that merge after the replacement are duplicates; an integer literal of more than 19 digits is refused unparsed; a float that underflows to 0 is accepted (it fits a double); an input whose stdin is closed, a directory or write-only is `payload_invalid` (pointer `""`), a `--file` that cannot be opened, read or is not a regular file is exit 2; `NOTICE_ROUTE_HOOK` counts as set when present, even empty; a notice `link` is at most 1024 characters, `http://` or `https://` followed by zero or more characters of `[\x21-\x7e]` (no space), 1024 characters in all; a `labels` value of `null` counts as not an array; a lone surrogate from argv in `--label` becomes U+FFFD and fails the grammar; a label with a valid grammar given twice, in the payload, the flags or both, counts once and adds nothing to `labels_ignored`; `event_id` and `object_id` accept an integer of the reader's range or a plain string and are `null` otherwise.

## Data model

See [Files](interface.md#files). Migrations are versioned and additive. Rows are updated in place; repeats are counted, not stored. Every table is bounded: queue 100 unclaimed rows per destination, `deliveries` and `event_ids` 100000 rows each, enforced on insert, at most 16 stored labels per row, dedup rows until their window ends or their delivery fails. The queue row carries rendered text only until its delivery, expiry or drop. A destination's identity in every table is its name; renaming a destination in config starts a fresh history for it.

C-44: the state database (#14). `Gateway.prepare_state_db` does every filesystem check on descriptors (directory 0700 and owned; `state.db` opened with `O_NOFOLLOW`, regular, owned, mode 0600, one link; `-wal`, `-shm` and `-journal` the same by `lstat`) because SQLite opens by path and cannot use `O_NOFOLLOW`; `store.py` then connects, which keeps `sqlite3` and the schema out of the gateway. `user_version` counts applied migrations and `application_id` marks the file as ours; a file with another `application_id`, a newer `user_version`, a missing table, or SQLite's own refusal is a `StoreError` (so is a read-only open of an older `user_version`, which only a writing open migrates; an empty file is no database for read-only opens) whose text is a fixed sentence per reason. The open path has one deadline on the gateway clock and each stage waits only for what is left of it. Migrations run in one `BEGIN IMMEDIATE` transaction that re-reads the version, so two first-run processes cannot both create the tables, and a crash leaves the old version. The connection is in autocommit with `query_only` on and `Store.write` is the only way to write (`BEGIN IMMEDIATE`). Pragmas: `foreign_keys`, `trusted_schema` off, `cell_size_check`, `secure_delete` (a row's text is overwritten when the row goes), `synchronous=NORMAL`, WAL, memory temp store; defensive mode and low SQLite limits (no `ATTACH`). `quick_check` (about 0.1 s at 100000 rows) runs only before a migration and through `Store.check_integrity`, not on every open, to keep `send` inside its 0.5 s transaction. `surfaced.period` is `YYYY-MM-DD`, or `YYYY-MM-DDThh` for the hourly codes, and `(destination, code, period)` is unique, which enforces the once-per-period surfacing limit. `dedup` is unique per `(destination, key_digest)` and `event_ids` per `(destination, source, hook, event_id, repeat_digest)`. Only `queue.delivery_id` has a foreign key: `surfaced`, `dedup` and `event_ids` rows may outlive their `deliveries` row.
C-45: quiet-hour window (#15), `window.py`. Choices where the interface is silent, all the narrower reading: an instant is UTC epoch seconds (an `int` or finite `float`, floored, never a `bool`, within a range that keeps the zone conversion and the two-day search inside `datetime`); the next end is a multiple of 60 epoch seconds, strictly after the instant, and is `None` only when no minute in the next 2 days is outside, which a valid window never produces, so a caller treats `None` as an internal error and never as permission to skip the check; a malformed window is a `ValueError`. Before 1972 some zones have offsets in seconds, so a multiple of 60 epoch seconds is then not a local whole minute; that is a documented choice, not a defect, and `window_end` still returns an instant outside the window. Both passes through a fall-back fold are judged by the rule, so a start or an end in the fold applies twice.

C-46: queue rows, claims and the cap (#16), `queue.py`: data-layer operations on the connection of a `Store.write` transaction, the clock passed in as a `Lease` (floored wall seconds and twice the rounded-up `send_worst_case_s`). A claim is live while `now < claim_expires <= now + lease length`: a wall clock that stepped back makes a claim whose remaining time exceeds one lease lapse (the row is resent, at least once) so a lease is never longer than its length and a row never waits for the clock to catch up; a missing claimant or expiry is a lapsed claim. A recorder is fenced by its token alone (`claimed_by` equals it), whether or not its own lease lapsed: a takeover writes a fresh token, and an unclaimed-but-lapsed row nobody took still accepts its claimant's result. A release sets `claim_expires` to the minimum of its value and now and keeps `claimed_by`. The cap counts unclaimed rows through `deliveries.destination` (no column added; migration 1 is unchanged), picks victims by lowest level, then lowest row id (age is the id, which clock steps cannot reorder; "oldest" means lowest row id everywhere, so `claim_due` also sends lowest id first), deletes the queue row and sets its delivery `dropped`/`overflow`/`overflow` (and `deliver_after` to NULL) in the same transaction. Accepted consequences, all duplicate-or-delay and never a lost row: a claim lapsed only because of a clock step (or written by a bad process with a far-future expiry) counts as unclaimed, so it can be evicted, and a notification can then be sent while its delivery is recorded dropped/overflow and its result goes to the log only (excluding such rows from eviction would leave a far-future row neither claimable nor evictable); a lapsed claim nobody took over still accepts its claimant's result; a released row keeps `claimed_by`, so after a backward step of less than the lease length it can look claimed for up to that long (a delay, and the cap count may briefly exceed 100); a `Lease` built before the write lock is held can have an earlier `now` than a concurrent claimant and read its live claim as lapsed (callers build it inside the `Store.write` block), and a config change that shortens `send_worst_case_s` makes in-flight claims made under the longer lease read as lapsed until they expire; the predicate adds no skew slack. `release_claims` returns the number of rows still carrying the token, not only those whose expiry changed. Dedup records of an evicted delivery (#17) and the `overflow` surfacing (#27) are seams. `insert_delivery` inserts a `deliveries` row and calls `trim_deliveries` with `keep_id`.

## Queue and row model

Every notification a destination will receive later is one queue row of kind `held` (quiet hours or the cap; folded into a digest) or `single` (everything else; always sent as itself). A row is claimed by the transaction that decides to call it, in `send` and in `flush` alike, and every result is recorded only on the row the recorder still holds. The 100-row cap counts unclaimed rows only and is applied by every transaction that leaves a row unclaimed. Event-id and repeat records live exactly as long as their delivery is pending, `sent` or `unknown`. Surfacing only writes a `surfaced` row; the next `flush` routes the alert and runs the `post-fail` hooks, so `send` never runs a hook and its time bound holds. `flush` writes a heartbeat that `validate` and `send` read, so a dead cron is visible. The rules are in [Deferral and digest](interface.md#deferral-and-digest), [Dedup](interface.md#dedup), [Retries and outcomes](interface.md#retries-and-outcomes) and [Hooks](interface.md#hooks).

## Concurrency

Any number of `send` and `flush` processes may run at once. The decision step is one `BEGIN IMMEDIATE` transaction with a 0.5 second busy timeout in `send` (two transactions, the 1 s of the time bound) and 5 seconds elsewhere; `prune` deletes in batches of 1000. It also writes the queue rows of the destinations to be sent now. The send step is serialized per destination by `flock`, and all `wsl-notice` destinations share `locks/_wsl.lock`. Every call claims its rows (a lease of twice `send_worst_case_s`), and a result is recorded only on rows the recorder still holds; `flush` resends a row whose claim expired. A `flush` holds a per-destination flush lock for its whole run, and per call the send lock and a claim. Every full `flush` records its start in `meta.flush_last`; `validate` and `send` read it to report a stopped cron. Deviation from design guide section 4.3: per-destination locks are kernel `flock`s, not leases in `state.db`; the kernel releases them when the holder dies, which is the property a lease provides. Queue rows carry leases (claims). Exact PIDs the router started are the only processes it signals, as process groups it created.

## Error handling

Failures are values: every call ends in one of the outcomes of [Retries and outcomes](interface.md#retries-and-outcomes), recorded in `history` and `log.jsonl`. State problems fail closed as [Files](interface.md#files) says: nothing is sent when the database cannot be used. Config errors fail fast with the key named and never the value.

## Test strategy

- Every subprocess, lock and clock use goes through `gateway.py`; tests substitute fakes. Fake notifiers live in `tests/fakebin/` and can exit with any code, print any envelope, sleep, ignore SIGTERM, spawn a grandchild, close stdin early and write oversized output.
- `--json` outputs have golden files and are validated against `schemas/`; the sibling notifiers' error envelope and `send` schemas, with their `defs.json` and `notification.json`, are copied into `tests/` at a pinned version.
- Process tests run in CI: group kill with a grandchild, the bounded reader, `flock` serialization across 8 processes including a SIGKILLed holder, concurrent `send` and `flush` claiming each row once, SIGKILL after the decision transaction and before the call (the row is sent by the next `flush` and a redelivery of the same `event_id` is `redelivered`), SIGTERM before the call (claims cleared, exit 128+N), two `flush` on one destination with 40 due rows (each row sent once), the dedup statement under 8 writers.
- Spike regressions: the window brute force as a property test; the strict reader cases; the template non-re-expansion case; bad time zone keys; the fixture "New York, 2026-11-01, window 22:00 to 01:30: inside until 01:30 EDT, inside again 01:00 to 01:30 EST".
- Behavior cases: a `failed` first send, then the next identical notification inside the window is sent; agent-spawn and claude-session both send `event_id: 41` to one destination, and both are sent; an evicted (`overflow`) and an `expired` row: the producer's redelivery of the same event is sent; a release after a later window opened with the same key leaves the later window.
- Queue and flush cases: a `send` stalled past its lease (SIGSTOP), `flush` resends and records `sent`, the stalled `send` resumes: `sent` stays; `prune` and an overflow eviction during a `flush` call leave the claimed rows alone; a quiet destination with one due `error` and ten `warn` rows: the `error` is sent, state `done`, the `warn` rows get the window's end; an `info` held for the cap and due in quiet: `dropped`, `quiet`; every destination `already_running`: exit 0; SIGTERM during a `flush` call; a config with no `flush` for 6 minutes: `validate` warns `flush_stale`, and an `env_missing` send prints the advisory line.
- Outcome table: one case per row, plus exit 0 with oversized stdout (row 3), exit 20 with garbage stdout (row 9), `generic` exit 22 (row 6), SIGKILL from outside (row 4), exit 143 (row 18).
- Database timing: a `prune` of 100000 rows and 8 concurrent `send`s: no `send` waits more than 0.5 s per transaction; the record transaction fails after a call: exit 1, the row is resent by `flush` once.
- Text and config cases: sanitize: tab becomes a space; a ZWJ emoji survives; a title of U+3164 renders empty and the message fallback applies; a NUL in literal template text becomes a space; an overnight window with `days: [fri]`: Saturday 02:00 inside, Sunday 02:00 outside; a symlink to a user-owned venv script passes and the resolved path runs, and the same with a group-writable directory on the resolved path fails `exec_failed`.
- Fake notifiers also include a double fork with `setsid` holding stdout.
- The example config and the drop-in are validated as one config and rendered in CI against hook payload examples written in this repository and validated against pinned copies of the producers' hook schemas; any `missing` or `excluded` token fails.
- `live` tests (deselected, never in CI): the real notifier trio, a marked test to the user's own Slack direct messages only.
- `make verify` runs ruff, pyright, pytest and markdown lint, and checks that every relative link in `docs/` and the README resolves. CI is Linux only; macOS is checked locally.
