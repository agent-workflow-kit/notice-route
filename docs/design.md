# notice-route: design

Status: designed 2026-11-17 against architecture v1.24, revised after review. The normative rules are in [interface.md](interface.md); this document records why, and how the tool is built. It links to interface headings and does not restate their tables.

## Role and layer

Layer 2 (composite). Routes notifications to channel notifiers by source, labels, level and time, with quiet hours, deferral, dedup, a per-destination rate cap, retries and a history. It works fully standalone: it needs only a command that accepts `send --stdin-json`, and the three notifiers we ship are the natural targets. It has no upward awareness: a producer reaches it through a hook line in the producer's own config, and nothing in the router knows who that producer is beyond the `tool` name in the payload.

## Uses

| Dependency | Binding | Notes |
|---|---|---|
| slack-notice, ha-notice, wsl-notice | B (configurable command) | Each destination names a command; the call shape is fixed (`send --stdin-json --json --actor auto:notice-route [--dedupe-key=<hex>]`). A `kind` selects the retry rules. See [Destinations](interface.md#destinations) and [Calling the notifiers](interface.md#calling-the-notifiers). |
| any other notifier | B, `generic` kind | Works when it accepts the call's words and reads the notification JSON from stdin; otherwise a wrapper script. No adapter code is shipped. |
| a time-zone database | system | `zoneinfo` from the standard library with the system database. |

The architecture entry for this tool said "binding C (adapters)" and also fixed the call shape, which is binding B. The call shape wins (D-6), and the architecture entry is corrected in v1.24. No other tool is a dependency: pr-watch, review-watch, ticket-work, agent-spawn and the rest reach the router only through hooks wired in their own configs.

## Decisions

| ID | Decision | Rationale | Interface |
|---|---|---|---|
| D-1 | Two input shapes told apart by keys, no mode flag; `payload_unrecognized` and `source_mismatch` refusals. | One documented hook line; a script cannot rename another tool's events. A rule without `message` passes a notice's own text through. | [Input shapes](interface.md#input-shapes) |
| D-2 | First matching rule wins; a rule can fan out to up to 8 destinations or `drop`. | One rule explains a routing; adding a rule cannot silently duplicate sends. | [Rules](interface.md#rules) |
| D-3 | The rule decides the level; the notice's own level is only a fallback; no `--level` flag. | A script cannot claim `error` to bypass quiet hours on a rule that fixes the level. A rule that can match a hook payload must set `level`. | [Levels](interface.md#levels) |
| D-4 | Templates are a single-pass `{{field}}` substitution. A payload value goes into a title only when it is plain (a number, a boolean, or a word-like string of letters, digits and `._/#-`); other text reaches only a message, through `include_text`, for payloads with `reads_third_party: false` and `tainted: false`. | The value is judged, not its field name, so a new free-text field fails closed without a list that tracks every producer; "what the agent asked" stays possible. | [Untrusted text](interface.md#untrusted-text), [Templates](interface.md#templates) |
| D-5 | Links come only from `links` tables and fixed payload ids. | A producer cannot aim the tap target, and a rule's link is one derived token or a literal URL. | [Links](interface.md#links) |
| D-6 | A destination is a command (binding B) with `kind`, `floor`, `quiet`, `max_per_hour`, `env`. | The call shape is fixed; adapters would track each notifier's changes. | [Destinations](interface.md#destinations) |
| D-7 | Named quiet windows referenced per destination; `timezone` required; wall-clock minute-of-day rule; only `error` bypasses. | A phone should be quiet while a desktop toast is harmless; spike A. | [Quiet hours](interface.md#quiet-hours) |
| D-8 | Notifications deferred for quiet hours or the cap are `held` queue rows, folded into one digest per destination titled `N held notifications`; at most 100 unclaimed queue rows per destination; rows 24 hours old or more expire. | Fifteen buzzes at 07:00 defeat quiet hours. Lines name the event (title and message head) and put the highest level first. | [Deferral and digest](interface.md#deferral-and-digest) |
| D-9 | Two dedup checks per destination: redelivery by source, hook, `event_id` and the repeat digest, and a fixed-window repeat check keyed on the notification as it would be sent (level included); its digest is passed as `--dedupe-key=<hex>`. | Two notifications that look the same are one; any field that shows makes them two, without a list of producer fields. A sliding window suppresses a steady repeater forever. Event ids are compared per source and hook, because producers number them independently. Records live while their delivery is pending, sent or unknown, so an undelivered notification never mutes its own redelivery. The digest stops a forged future id from muting the real event. | [Dedup](interface.md#dedup) |
| D-10 | Every notification a destination will receive later is a queue row (`held` or `single`) claimed by the call that sends it, and a send-now decision is a `single` row written before its call; retries go through the queue and `flush` with a fixed schedule; a possibly-sent outcome is never retried (ha-notice's both-true excepted). | A hook-run `send` must end quickly; retrying a possibly-sent Slack message duplicates it. A crash during a call is the one case that resends (at least once). A notifier ended by a signal it did not report is treated as possibly sent. | [Retries and outcomes](interface.md#retries-and-outcomes) |
| D-11 | Exit 0 means the router took responsibility for every destination; 12 means a definite failure or unknown outcome; 22 means nothing to do. | Scripts can tell a failure from quiet hours or dedup. | [Exit codes](interface.md#exit-codes) |
| D-12 | History keeps the rendered title of a templated rule (literal text and plain values only) and hashes; message text is deleted with its queue row; no `audit.jsonl`. | Free text never rests on disk after delivery; stored ids and labels are plain or label-grammar values. | [Files](interface.md#files), [Log](interface.md#log) |
| D-13 | Config and state are found only from the password-database home; owned-by-user and no group or world write; no per-repo or environment layer; `--config` only on commands that run nothing. | The config selects commands that run with credentials in their environment. `--config` is accepted only by commands that run nothing, and a sandboxed session is never allowed `send`, because `send` writes the state directory that `flush` delivers from. | [Environment variables](interface.md#environment-variables), [Config](interface.md#config) |
| D-14 | One hook, `post-fail`, run by `flush`, with a recursion guard on `NOTICE_ROUTE_HOOK`; surfaced failures are also routed through the rules as source `notice-route`. | A way to learn a channel is down without a loop, with quiet hours, floors and credentials applied like any other notification. Surfacing only writes a row; `flush` routes the alert and runs the hooks, so `send`'s time bound never includes a hook. | [Hooks](interface.md#hooks) |
| D-15 | Eight commands; no `queue` or `destination` management in 0.x; `test` is explicit, never sends and takes `send`'s input flags. | Each command has one job; management is state reachable by config and `history`. | [Commands](interface.md#commands) |
| D-16 | Process model: parallel across destinations, serialized per destination by `flock`, own process group, bounded output, monotonic deadline, group kill. | Spike B. | [Calling the notifiers](interface.md#calling-the-notifiers) |
| D-17 | A per-destination counter of calls claimed per UTC hour, kept separately for `error` and for the other levels; a notification over the cap is held for the next hour and folded into a digest. | Dedup stops repeats, not a flood of distinct events. A flood of non-errors cannot delay an `error`, and eviction drops the lowest level first. A digest is never held by the cap, so held rows cannot starve. | [Rate limit](interface.md#rate-limit) |
| D-18 | No built-in rules or destinations; `config.example.yaml` plus the drop-in are a complete worked config. | A built-in rule would silently change who is pinged when a producer's enum list changes. `validate` knows no producer; the example is checked in CI. | [Config](interface.md#config) |

## Calls made by the author

Decisions the user did not see as choices, made while writing and open to correction:

- C-1: the whole-call budget of the approved model bounds only the lock wait (a started call runs to its deadline); `lock_wait` defaults to 2s, a `send` makes at most one call per destination, and the worst case is 29 s with defaults, counted from the end of input, under the hooks' 30 s default. `validate` prints the figure; the bound excludes input reading and every hook (hooks run from `flush`).
- C-2: a destination's `timeout` is at least the notifier's own; the router cannot read the notifier's value.
- C-3: input limits for the strict reader (1 MiB, depth 16) and label grammar (producer-compatible, up to 64 payload labels read and 32 `--label`).
- C-4: the retry schedule (1 m, 5 m, 30 m, 2 h counted from the end of the previous call; 5 attempts, 3 for wsl-notice, its caller contract), digest size (10 lines), the 24 hour expiry; `lock_busy` counts no attempt and is due again after 60 s; after a retryable, `failed` or `unknown` result `flush` stops calling that destination for the run (its other due rows wait for the next run); one 100-row cap covers the unclaimed `held` and `single` rows; immediate retries go through the queue and count as attempts.
- C-5: the cap counts calls claimed (failures too) in the current UTC hour; a digest counts in its highest class and is never held.
- C-7: `post-fail` is best-effort, at most once, run by `flush`, with no outbox in 0.x (1.x adds an outbox for synchronous hooks, C-62); expiry, overflow, the cap and a missing credential are surfaced too.
- C-8: a label on a payload that does not fit the grammar is ignored and counted, not refused.
- C-9: exit 20 for payload faults only; `config_unsafe` and bad config are exit 2.
- C-10: pass-through rules require `level_min`, and messages are cut at 4000 characters.
- C-11: a `send` or `flush` that lacks a destination's credential never calls it: `send` queues the notification as a single row due now, `flush` leaves the rows and surfaces `env_missing`; an empty value counts as unset.
- C-13: every call claims its rows and a crash resends (at least once).
- C-14: drop-ins append `rules` and `hooks.post-fail`, merge destination, window and link entries by name, and refuse anything defined twice.
- C-15: the digest title is `N held notifications`.
- C-16: the row caps are 100000 per table, enforced on insert; retention settings are at least 1 day.
- C-17: input from stdin must be complete within 5 seconds of the start of the command, and a lone surrogate is replaced, not refused.
- C-18: a top-level `enabled` key disables the router.
- C-19: a rule that can match a hook payload must set `level`; a rule that does not is a load error, not a warning.
- C-20: `test` takes `send`'s input flags instead of a separate `--input` flag.
- C-21: every call claims its rows and `lock_busy` counts no attempt.
- C-22: the per-destination health that `validate` shows is `surfaced_today`.
- C-23: the row kinds `held` and `single` and the cap on unclaimed rows.
- C-24: the lifetime of the dedup and event-id records: pending, sent or unknown.
- C-25: alerts skip the redelivery check, and row ids are never reused.
- C-26: the outcome table in precedence order, with a code for every row.
- C-27: refusal retries (link, keyword) count as attempts.
- C-28: a digest is never held by the cap.
- C-29: hooks and alerts run from `flush`; `send` runs none.
- C-30: surfacing periods (queue events hourly, other codes daily) and the limit of 8 codes.
- C-31: the alert payload fields `notification_source` and `notification_level`.
- C-32: `send`'s 0.5 s busy timeouts, two transactions.
- C-33: global row caps on insert and at most 16 stored labels.
- C-34: the plain grammar `[A-Za-z0-9][A-Za-z0-9._/#-]{0,255}`.
- C-35: one sanitizing routine for every rendered title and message.
- C-36: drop-ins merge map entries by name.
- C-37: the `flush` heartbeat read by `validate` and `send`, written only by a full run (no `--dry-run`, no `--destination`), with a record of whether the run skipped a destination for a missing credential.
- C-38: the last fixes narrow rules and add none: the cron block starts at a line that begins `# notice-route managed v`, `send`'s advisory needs a queued row, a wrapper must `exec` the notifier and exit 128+N with output is `unknown`, the hook environment is an allowlist like every child's, and `flush` stops calling a destination after `failed` or `unknown`.
- C-39: config loading (#6): the strict loader keeps PyYAML's scanner and parser (the one runtime dependency; C-42 drops `pydantic`) and replaces its resolvers and constructors: only `true` and `false` are booleans, only decimal integers and decimal floats are numbers, and `null`, `Null`, `NULL`, `~` and the empty value are null, so `yes`, `on`, `True`, `010`, `1e3`, `.inf` and dates stay strings. It refuses anchors, aliases (at the first one met, so nothing expands), explicit tags, merge keys (`<<`), duplicate keys, keys that are not strings, lone surrogates and NUL in a string, more than one document, a null document (only an empty or comment-only file is an empty config) and nesting deeper than 16 (the reader's depth, C-3). The YAML error text quotes the file, so it is never kept (not as `__cause__` or `__context__`).
- C-40: `details.key` for config errors: a known key path, an entry name under `destinations`, `quiet_hours`, `links.hosts` or `links.tickets` when it is plain (`[A-Za-z0-9][A-Za-z0-9._-]{0,63}`), `?` for any other key (an unknown key may be a secret pasted as a key; nothing after a `?` is shown), `rules.<index>.name` for a rule name defined twice, `home`, `--config`, `.` for the config directory, `config.d`, and a file path relative to the config directory (`config.yaml`, `config.d/<name>` with every character outside `[A-Za-z0-9._-]` shown as `?`, so two distinct names can show the same key). A `--config` file's own problems are keyed `--config`.
- C-41: the config directory and `config.d` are opened with `O_NOFOLLOW`, so a symlinked directory (a dotfile manager's link) is `config_unsafe`, like a symlinked file; group or world read access is fine, write access is not. A missing `--config` file is `config_invalid` (key `--config`), not `unconfigured`: the user named it. A missing `config.yaml` is `unconfigured` even when `config.d` has files (drop-ins alone configure nothing, and are not read). Drop-ins are the visible `*.yaml` names in `config.d` (not `.yml`, not hidden, not backups), in code point order; a rule name defined twice is refused also within one file; a `null` where `rules`, `hooks.post-fail`, `destinations`, `quiet_hours`, `links.hosts` or `links.tickets` belongs is `config_invalid`; maps merge key by key, and a leaf defined in two files is `config_invalid` (so `retention.history` and `retention.event_ids` may sit in different files). Only the last component of a directory path is `config_unsafe` when it is a symlink or not a directory; a non-directory earlier on the way is a missing directory (`unconfigured` for the home location, `config_invalid` key `--config` for `--config`), and a `--config` whose last segment is empty, `.` or `..` is `config_invalid`. The reader limits are 256 KiB per file, 1 MiB for all files together (conservative, like the 1 MiB reader limit of C-3; the file whose read crosses it is `config_invalid`), 256 drop-ins and 4096 directory entries of any name in `config.d`; an integer or float of more than 20 characters (sign excluded) is `config_invalid`, and only mappings and sequences count toward the depth limit of 16.
- C-42: config validation (#7) is a hand-written validator in `validate.py` that builds frozen dataclasses (`Config`, `Destination`, `QuietWindow`, `Links`, `Rule`, `Match`, `Hook`), not `pydantic`: its error text quotes values and its error locations name unknown keys, both of which C-40 forbids, and a second runtime dependency would buy only the type checks written here. `load_config` still returns the raw merged mapping; `validate_config(data, gateway)` and `load_valid_config` build the typed config, so the loader's tests keep their small fixtures. The key of a problem is its path (`rules.<index>.<key>`, `destinations.<name>.<key>`); a problem inside a list, a `where` map or a `labels` list is keyed by the list or map, never by an element, and a missing required key is keyed by that key (a pass-through rule without `level_min` by `rules.<index>.match.level_min`). Time zones load through `Gateway.load_zone`: only the system database directories, the file read and parsed from memory, so `PYTHONTZPATH` and `zoneinfo.TZPATH` play no part. Choices where the interface is silent, all the narrower reading: a pass-through rule may carry only a literal `link` (the tokens need a payload, which a notice has not); a `post-fail` hook's `cmd` is 1 to 4096 characters and its `timeout` is 1s to 1h; a destination's `env` has at most 4096 entries (spec clarifications, also in `docs/interface.md` and `schemas/config.json`); `retention.*` is at most 100 years; `labels`, `notify`, `env`, `days` and `include_text` list entries must be unique and `labels` and `include_text` non-empty when present (as `schemas/config.json` says); a `cmd[0]` is `/` plus at least one character.
- C-43: input reading (#8) is `payload.py`, one strict reader (`parse_json_object`) that the notifier-output parser reuses; the gateway reads (`read_stdin` with an absolute monotonic deadline of start plus 5 s, `read_input_file` that follows symlinks and checks the opened descriptor, `stdin_is_tty`, `env_present`). Choices where the interface is silent, all the narrower reading: a lone surrogate in a key is replaced before the duplicate check, so keys that merge after the replacement are duplicates; an integer literal of more than 19 digits is refused unparsed; a float that underflows to 0 is accepted (it fits a double); an input whose stdin is closed, a directory or write-only is `payload_invalid` (pointer `""`), a `--file` that cannot be opened, read or is not a regular file is exit 2; `NOTICE_ROUTE_HOOK` counts as set when present, even empty; a notice `link` is at most 1024 characters, `http://` or `https://` followed by zero or more characters of `[\x21-\x7e]` (no space), 1024 characters in all; a `labels` value of `null` counts as not an array; a lone surrogate from argv in `--label` becomes U+FFFD and fails the grammar; a label with a valid grammar given twice, in the payload, the flags or both, counts once and adds nothing to `labels_ignored`; `event_id` and `object_id` accept an integer of the reader's range or a plain string and are `null` otherwise.

## Data model

See [Files](interface.md#files). Migrations are versioned and additive. Rows are updated in place; repeats are counted, not stored. Every table is bounded: queue 100 unclaimed rows per destination, `deliveries` and `event_ids` 100000 rows each, enforced on insert, at most 16 stored labels per row, dedup rows until their window ends or their delivery fails. The queue row carries rendered text only until its delivery, expiry or drop. A destination's identity in every table is its name; renaming a destination in config starts a fresh history for it.

C-44: the state database (#14). `Gateway.prepare_state_db` does every filesystem check on descriptors (directory 0700 and owned; `state.db` opened with `O_NOFOLLOW`, regular, owned, mode 0600, one link; `-wal`, `-shm` and `-journal` the same by `lstat`, except that a file with no links left counts as absent: `lstat` can see one while a sibling unlinks it, because the kernel drops the link count before the name, #63) because SQLite opens by path and cannot use `O_NOFOLLOW`; `store.py` then connects, which keeps `sqlite3` and the schema out of the gateway. `user_version` counts applied migrations and `application_id` marks the file as ours; a file with another `application_id`, a newer `user_version`, a missing table, or SQLite's own refusal is a `StoreError` (so is a read-only open of an older `user_version`, which only a writing open migrates; an empty file is no database for read-only opens) whose text is a fixed sentence per reason. The open path has one deadline on the gateway clock and each stage waits only for what is left of it. Migrations run in one `BEGIN IMMEDIATE` transaction that re-reads the version, so two first-run processes cannot both create the tables, and a crash leaves the old version. The connection is in autocommit with `query_only` on and `Store.write` is the only way to write (`BEGIN IMMEDIATE`). Pragmas: `foreign_keys`, `trusted_schema` off, `cell_size_check`, `secure_delete` (a row's text is overwritten when the row goes), `synchronous=NORMAL`, WAL, memory temp store; defensive mode and low SQLite limits (no `ATTACH`). `quick_check` (about 0.1 s at 100000 rows) runs only before a migration and through `Store.check_integrity`, not on every open, to keep `send` inside its 0.5 s transaction. `surfaced.period` is `YYYY-MM-DD`, or `YYYY-MM-DDThh` for the hourly codes, and `(destination, code, period)` is unique, which enforces the once-per-period surfacing limit. `dedup` is unique per `(destination, key_digest)` and `event_ids` per `(destination, source, hook, event_id, repeat_digest)`. Only `queue.delivery_id` has a foreign key: `surfaced`, `dedup` and `event_ids` rows may outlive their `deliveries` row.
C-45: quiet-hour window (#15), `window.py`. Choices where the interface is silent, all the narrower reading: an instant is UTC epoch seconds (an `int` or finite `float`, floored, never a `bool`, within a range that keeps the zone conversion and the two-day search inside `datetime`); the next end is a multiple of 60 epoch seconds, strictly after the instant, and is `None` only when no minute in the next 2 days is outside, which a valid window never produces, so a caller treats `None` as an internal error and never as permission to skip the check; a malformed window is a `ValueError`. Before 1972 some zones have offsets in seconds, so a multiple of 60 epoch seconds is then not a local whole minute; that is a documented choice, not a defect, and `window_end` still returns an instant outside the window. Both passes through a fall-back fold are judged by the rule, so a start or an end in the fold applies twice.

C-46: queue rows, claims and the cap (#16), `queue.py`: data-layer operations on the connection of a `Store.write` transaction, the clock passed in as a `Lease` (floored wall seconds and twice the rounded-up `send_worst_case_s`). A claim is live while `now < claim_expires <= now + lease length`: a wall clock that stepped back makes a claim whose remaining time exceeds one lease lapse (the row is resent, at least once) so a lease is never longer than its length and a row never waits for the clock to catch up; a missing claimant or expiry is a lapsed claim. A recorder is fenced by its token alone (`claimed_by` equals it), whether or not its own lease lapsed: a takeover writes a fresh token, and an unclaimed-but-lapsed row nobody took still accepts its claimant's result. A release sets `claim_expires` to the minimum of its value and now and keeps `claimed_by`. The cap counts unclaimed rows through `deliveries.destination` (no column added; migration 1 is unchanged), picks victims by lowest level, then lowest row id (age is the id, which clock steps cannot reorder; "oldest" means lowest row id everywhere, so `claim_due` also sends lowest id first), deletes the queue row and sets its delivery `dropped`/`overflow`/`overflow` (and `deliver_after` to NULL) in the same transaction. Accepted consequences, all duplicate-or-delay and never a lost row: a claim lapsed only because of a clock step (or written by a bad process with a far-future expiry) counts as unclaimed, so it can be evicted, and a notification can then be sent while its delivery is recorded dropped/overflow and its result goes to the log only (excluding such rows from eviction would leave a far-future row neither claimable nor evictable); a lapsed claim nobody took over still accepts its claimant's result; a released row keeps `claimed_by`, so after a backward step of less than the lease length it can look claimed for up to that long (a delay, and the cap count may briefly exceed 100); a `Lease` built before the write lock is held can have an earlier `now` than a concurrent claimant and read its live claim as lapsed (callers build it inside the `Store.write` block), and a config change that shortens `send_worst_case_s` makes in-flight claims made under the longer lease read as lapsed until they expire; the predicate adds no skew slack. `release_claims` returns the number of rows still carrying the token, not only those whose expiry changed. The dedup records of an evicted delivery are released by `enforce_cap` (C-47); the `overflow` surfacing (#27) is a seam. `insert_delivery` inserts a `deliveries` row and calls `trim_deliveries` with `keep_id`.

C-47: dedup (#17), `dedup.py`: data-layer operations on the connection of a `Store.write` transaction, `now` and the retention passed in as integers. The repeat check is one upsert statement (`check_repeat`) that opens a window or replaces one that is not active and returns no row for an active one, so a suppressed repeat adds 1 to `count` of the opener (not past int64) and nothing else changes. A window is active only for `start <= now < start + length`: after a backward clock step a window that would outlast its length from now is not trusted (duplicate, never lost; the narrow reading, as the lease of C-46). The window has no `delivery_id` until `bind_window` (the delivery row is inserted after the decision); bind before queueing, because queueing may evict and eviction calls `release`. A replaced window carries the new delivery id, so the old delivery's end releases nothing of it. An event id is the `json.dumps` text of a plain id (an int, never a bool, or a plain string; an integer past Python's text limit is ignored); source `notice-route` is neither checked nor recorded. A record is live for `now - retention <= seen_at <= now` (what `prune` keeps; a future record after a backward step is not trusted); recording never extends a live record (the upsert replaces only a record that is not live, and returns `False` for a live one, so a race or a caller that skipped the check is no error), and then trims the table with `trim_event_ids(keep_id)`. `release(delivery_id)` deletes both records and is called by `enforce_cap` for each evicted delivery in the same transaction (an evicted delivery ends `dropped`, which releases). The repeat digest stays `dryrun.dedupe_digest`; the functions require 64 lowercase hex. Migration 1 is unchanged. Durations are integer seconds: `dedup.py` rejects a float, and the caller converts a configured duration once with `math.ceil` (#18). `bind_window` refuses (returns `False`) and deletes the still-unbound window when its delivery row is missing or already ended `failed`, `dropped`, `expired` or `disabled` (for example self-evicted by the cap), so a repeat is never suppressed against a dead delivery; `record_event_id` requires a `delivery_id` (a record nothing releases would outlive a failed delivery). The cap on `event_ids` evicts by lowest row id (indexed, no sort); replacing a record that is not live gives it a fresh row id (`id = max(id) + 1` in the upsert), so a replaced record is not evicted before older ones. `RETURNING` needs SQLite 3.35 or newer (3.34 on Debian 11, 3.31 on Ubuntu 20.04 and 3.26 on RHEL 8 are too old): opening the store for writing with an older library is a `StoreError` ("SQLite 3.35 or newer is required"); a read-only open never uses `RETURNING` and still works, so only the writing commands need 3.35. Rows with a start or `seen_at` after `now` are not pruned until the clock reaches them; they are never trusted and are bounded by the caps (accepted). `count_prunable_windows` and `count_prunable_event_ids` share the predicate of the deleters, for the `prune` dry run. Seams: the decision order (#18: `check_repeat`, `insert_delivery`, `bind_window`, `record_event_id`, `enqueue`), the send pipeline (#22), and every delivery end except `sent` and `unknown` (`failed`, `dropped`, `expired`, notifier-side `disabled`) calling `release` in the same transaction (#20, #23 flush expiry, #26 prune expiry), `prune` loops (#26).

C-48: the decision order and the hourly counters (#18), `decide.py`. `decide_and_record` runs `send` step 7 for all destinations in one `Store.write` block (clock read and `Lease` built inside it, a fresh claim token per send-now row) and rolls everything back on any exception; `preview` runs the same classification for `test` and `send --dry-run` on a read-only connection (`open_readonly`) that `dryrun.dry_run_document` opens once the config is enabled and has destinations (a disabled or unconfigured router is exit 22 before any state read) and before a rule is matched, so a database that cannot be opened is exit 1 `internal` (a `StoreError`) for `test` and `send --dry-run` whatever the notification would decide (`no_rule`, a `drop` rule and all-disabled included); `preview` still opens lazily when it is given an opener, and the caller closes. C-49: the notifier call (#19), `notify.py`. `call_notifier` takes a rendered notification, the destination and the dedupe digest and returns a `CallResult` (`ran` with the `RunResult`, `env_missing`, `exec_failed`, `not_started`, `lost`); it decides, locks and counts nothing and keeps no exception text or environment value. `build_argv` takes no notification field (resolved `cmd[0]`, `cmd[1:]`, the fixed flags, `--dedupe-key=<64 lowercase hex>`); `build_env` reads only `Gateway.environ()` (fixed set plus the destination's `env` names; an unset, empty or NUL-holding value counts as unset); `notification_json` writes one ASCII line (`ensure_ascii`) of the present fields in the order title, message, level, link, so any text but a lone surrogate round-trips exactly; an empty message or a lone surrogate in title, message or link is refused (`ValueError`, so `not_started`), as the siblings refuse both. `ran` keeps the `RunResult` without `error` and without `stderr` (never stored). Seams: TODO(#22) pipeline.

C-50: classifying a call and recording its outcome (#20), `outcome.py`. `classify` is pure: a `CallResult` plus the destination kind and whether `--dedupe-key` was passed gives an `Outcome`, the first row of the table that applies. The exit code picks the row and the envelope only supplies flags and codes, so an envelope that disagrees with the exit code (an error envelope on exit 0 or 22, flags on exit 20) is ignored. The strict reader of `payload.py` parses stdout; on exit 12 and 1 both flags must be present booleans, on exit 20 no flag is read and `error.reason` must be present, and `error.code` (and the reason) must match `[a-z][a-z0-9_]{0,63}`, else the envelope is unparseable (row 9). A well-shaped code the router does not know is used as it is and the flags decide. Only fixed words, those pattern-checked codes and a pattern-checked `notifier_outcome` leave the notifier's stdout, so hostile text never reaches the log or history. Exit 22 is `disabled` whatever stdout holds (`notifier_outcome` null when unreadable; nothing is invented). `lost` is `unknown`/`killed` (the gateway killed the group); `not_started` is an internal fault that records nothing (the claim lapses and `flush` resends, no blind retry); `env_missing` at call time requeues the row `deferred`/`env_missing`, due now, with no attempt and the hourly count given back (decided from the outcome before any cap eviction, so a requeue the cap then drops still gives it back). `apply_outcome` (inside `Store.write`; `record_outcome` opens it and reads the clock after the lock) writes the `deliveries` row (outcome, code, attempts plus one for a call made, `reason` left as it was unless the outcome sets one) and deletes or requeues the queue row through `complete_row` and `requeue_row`, fenced by the claim token: a recorder that lost its claim changes nothing (result to the log only, `applied` false). `failed` and `disabled` release the dedup records in the same transaction; `sent` and `unknown` keep them; a requeue that the cap drops ends `dropped`/`overflow` (released by the cap). A retry asks `retry_at(attempts)` (the schedule, `retry.py`, C-55) and ends `failed`/`retries_exhausted` when it returns None. A refusal retry (rows 13 and 14) rewrites the queue row (link refused: no link, the message, a line break and the URL; keyword refused: `<source>: <message>`; cut to 4000, trailing spaces stripped) and follows the retry schedule like any retry (`retry_at(attempts)`): the interface names no exception to the 1 minute, 5 minute, 30 minute and 2 hour schedule, so that literal reading is used (C-55 settles the open question: a refusal retry is not due now). A row whose `reason` is already `link_refused` or `keyword_refused` that is refused again ends `failed` with the refusal reason as code, and a link refusal of a row without a link (nothing can cure it) also ends `failed` with that code; these checks come before the attempt cap, so the code is the refusal reason, never `retries_exhausted`. A non-refusal retry keeps the refused reason, so a later refusal still ends `failed`; an `env_missing` deferral never overwrites a stored refusal reason either. Every requeue (retry, refusal, `env_missing`) sets the row to kind `single`, so a held row that is retried is no longer held. The notifier's own codes pass verbatim, including the router-reserved ones (`env_missing`, `rate_capped`, `overflow`, `expired`, `retries_exhausted`, `killed`; forward compatibility): a caller must read `Applied.outcome` and `Applied.reason`, not `code`, to tell a router state from a notifier code. `notifier_outcome` is non-null when the stdout of an exit 0 or 22 call is a valid `{outcome}` and null otherwise (never invented), which interface.md and the `send` schema now say. On exit 1 an `error.code` of bad shape is `unknown`/`envelope_invalid` even when `unknown_outcome` is false (safe). The fence on the queue claim is checked before the delivery is read, so a stale claimant whose delivery was trimmed gets `applied` false. `not_started` records nothing, so the hourly count it took stays (nothing is known about whether the call ran; the 24 hour expiry and the cap bound it). The hourly count is given back only for a call that was never made and only when the caller passes `count_hour`. An exception that escapes `call_notifier` is `record_escaped`: `unknown`/`killed`, one more attempt, the queue row stays claimed (it lapses and `flush` resends: at least once). Seams: the schedule is done (C-55), done in C-57 surfacing (including the rows `record_escaped` leaves), TODO(#22) logging and the call pipeline. Migration 1 is unchanged.

C-51: the send lock (#21), `sendlock.py`. `send_lock(gateway, state, name, kind, lock_wait)` is a context manager yielding `Held(acquired, busy_reason)`; the lock is an exclusive `flock` on `locks/<name>.lock`, polled every 50 ms on the monotonic clock (`Gateway.try_lock`). Every `wsl-notice` destination uses the one lock `locks/_wsl.lock` instead of its own lock (no destination name starts with `_`), so a call never holds two locks and no lock order can deadlock; this deviates from one lock per destination for that kind only. An unusable `locks/` directory (symlink, not private, any `OSError`) and a bad lock file are `lock_busy` with `busy_reason` `unsafe` or `error` (a wait that ran out is `timeout`); nothing is sent. A bad destination name or an unknown kind is a `ValueError` (a programming error, raised before anything is opened), checked with the grammar and kinds of `validate.py`. Release runs on every path (unlock, file close and directory close each guarded, so a failure in one never skips the others or replaces the body's exception). A `lock_busy` outcome (`outcome.LOCK_BUSY`) ignores `retry_at` and the attempt cap: the row is requeued `deliver_after = lease.now + 60` with no attempt counted; the stored refusal reason (`link_refused`, `keyword_refused`) is kept in the `deliveries` column so a later refusal still ends `failed`, while `Applied.reason` is `lock_busy`; the hourly count is given back only when the caller passes `count_hour`. C-52: `send` end to end (#22), `send.py`, `log.py`, `cli.py`. The cli reads and validates the input and the config; `run_send` does the rest: decision (`decide_and_record`), one thread per send-now row (`send_lock`, then `call_notifier`), and the main thread records each result with `apply_outcome` in a transaction of its own as the calls finish (a SQLite connection is not shared between threads). Choices where the interface is silent, all the narrower reading. Signals: SIGTERM, SIGINT and SIGHUP are trapped for the whole command, output included; the trap is armed for the input read and config load (a signal raises at once and the exit is 128+N with nothing written), and from the store open on a signal only sets a flag. After the decision, a signal with send-now rows releases this process's claims and exits 128+N (the decided destinations are logged first). A signal that arrives while a call thread waits for its send lock does not start the call: a thread that gets the lock after the signal and before any call started releases its row and makes no call, and the command exits 128+N when no call started in any thread (otherwise the calls finish and the result is reported). Once any call has started, a signal only sets a flag and the result is reported; a late signal with no send-now rows is ignored and the exit reflects the result. The flag stays set (the trap stays installed) until the output is written, so a late signal never kills the process before its document is printed. During the output itself a signal ends the process at once with 128+N (the result is final and already recorded, so nothing is lost; the streams are pointed at the null device first), so a reader that stopped reading cannot hold the process in a blocked write until SIGKILL. An exception escaping a call thread (anything, `SystemExit` and `KeyboardInterrupt` included) is `record_escaped` (`unknown`/`killed`, row left claimed); its text is dropped. That holds only once the call was started: an exception from `send_lock` itself before any call (nothing was sent) releases the row with no attempt, is not logged and ends the command 1 (internal), like `not_started`. A result that cannot be recorded (a `StoreError` after one retry 0.2 s later when the claim has at least 0.8 s of life left, or any other exception from the recording, a failing surfacing seam included) leaves the claim to lapse, is logged with what the call said, prints a warning that a duplicate is possible and ends the command with exit 1 (over 12) after every other destination was handled and logged; a result whose claim was lost is logged and shown as classified (nothing is stored for a lost claim; the claimant that took the row decides). `not_started` records and logs nothing (the log has no outcome word for it) and is exit 1. `--quiet` drops only the advisory lines (the `no recent flush` line and `no config`); the per-destination stderr lines of a text run and the warnings stay. A text run prints nothing on stdout; `--verbose` adds one `decision` line per destination. The history row of `no_rule` and a drop rule is a `deliveries` row without a destination, level the notice's own level or `info`. `--config` is a global flag before or after the command; every command but `rules`, `test` and `validate` refuses it with exit 2. `--actor` must match the `actor` grammar and `--decision-id` may be given once (exit 2 otherwise); the default actor is `human:<login name>` when stdin is a terminal, else `auto:unknown`. `log.lock` belongs to `log.py`: an exclusive `flock` taken for one append and the rotation it may trigger, waited for at most 0.5 s, so `send`, `flush` and `prune` order their lines through `LogWriter`; a line that cannot be written is skipped with one warning. Delivery log lines of called destinations are written as their results are recorded; those of decided destinations (deferred, dropped, suppressed, disabled) after all results are in (or before the exit of a signal), so a line that waits up to 0.5 s for `log.lock` never delays a call. `duration_ms` is the time since the command started, on the monotonic clock: in the document, at its end; in a delivery line, when the line is written. A short write of a log line is cut back (`ftruncate` under `log.lock`) so no partial line glues to the next record. Output after the result is known (stdout, stderr) is best effort: a write error or a closed stream changes no exit code, and the stream is pointed at the null device so its buffered text cannot fail at exit. The hourly count given back for a call that was never made (`lock_busy`) is the hour of the decision (`DestinationDecision.decided_at`), not a later read. `send --dry-run` checks `--actor` and `--decision-id` like `send` (exit 2). Seams: the retry schedule (`retry.py`, C-55, injectable through `Seams.retry_schedule`) and surfacing a `failed` or `unknown` end (`Seams.surface`, called inside the recording transaction; done in C-57). The recording is retried once as a whole after a `StoreError`, so `surface` may run again after a rolled-back failure: it must write only through the connection it is given (a rollback undoes it) and have no external effect. Not handled here: rows evicted from other destinations' queues by the cap while requeueing are not logged by `send` (their `deliveries` rows are updated by `queue.py`); repeated escapes add an attempt each time and `send` makes at most one call per row per run, so the cap on them belongs to `flush`; done in C-55 (`retry.py`).

C-53: `flush` (#23), `flush.py`, `calling.py`, `sendlock.flush_lock` and the queue helpers. One thread per destination, each with a connection of its own (a connection is not shared between threads); the threads call and record, the main thread starts the run, writes the heartbeat and prints. The call path (`calling.call_row`: send lock, signal gate, call, unlock) and the recording (`send.record_result`: `apply_outcome` plus the surfacing seam in one transaction) are shared with `send`. Choices where the interface is silent, all the narrower reading: "heartbeat" is `meta` (`flush_last` before the work and `flush_env_missing` after it, only for a run that covers every destination without `--dry-run`); claims are not extended (a lease is twice the worst case and covers the lock wait and the call); a router with no config, no destinations or `enabled: false` reads and writes no state, so no heartbeat; A run that exits 1 (state database, a flush lock that cannot be used, a queue row that cannot be used, an internal fault in a destination thread) prints with `--json` the usual error envelope only, like every exit 1; the results of the destinations that finished are in the log and the database, and in text mode the other destinations' lines still print. `--dry-run` is an approximation: it does not model `max_per_hour` at claim time, so a destination whose due single rows are all at the hourly cap reports `done` in a dry run and `nothing_due` in a real run. C-54: digests (#24), `digest.py` and `flush._send_held`. `digest.build` is pure (rows in, title, message, level out); the head is the stored title or rule name, ` - ` and the first non-empty line of the message (after sanitizing, so a line of spaces is blank), cut together to 120 code points (the interface's "cut together"; the line is longer by its level and source; a cut drops a trailing space, a dangling separator dash and a trailing U+200D), and each part is sanitized again (a stored row is never trusted, never templated). Age is the row id (as for the queue cap), so a clock step cannot reorder lines. One transaction claims every usable due `held` row with one shared token (so a signal releases them all with `release_claims`) and counts one call in the class of the highest level with `count_call` (no cap check); a member whose attempts are used up (an escaped call that repeated) ends `failed`/`retries_exhausted` without a call and is left out, and fewer than two left means the lone row is sent as itself through the normal claim (the cap applies to it). A stored row with an invalid level is left out with the same warning and exit 1 as for single rows. `record_digest` applies the result to every member in one transaction, each fenced by the token, so a failure rolls back all members and they lapse and are resent together (the documented duplicate); a member whose claim was taken over is logged only. Members are recorded "as if sent alone" through `apply_outcome` with these differences: reason `digest` for ends and for a plain retry, decided on the result of this call, not on the reason a member had stored (a `lock_busy` or refusal result of this call keeps its own; `env_missing` found at call time sets `env_missing`); a `queued_retry` (a plain retry and `lock_busy`) leaves the rows `held` (`requeue_kind`) so they fold again, while `env_missing` members become `single` (interface: an `env_missing` row is `single`), and a keyword or link refusal rewrites each row (keyword: source prefix; link: link moved into the message) and makes it `single`; a retry schedule step is that of the highest attempt count among the members that still have attempts left (a member that has none ends `failed`/`retries_exhausted`); the hourly count the digest took is given back once, in the class of the digest's level, when a call was never made (`lock_busy`, `env_missing`) and at least one member was recorded. A member whose claim is lost, or whose rows are gone, is skipped before anything is read from it (the attempts count of a plain retry is taken only from members still claimed). An escaped call leaves every member `unknown`/`killed`, reason `digest`, one more attempt, still claimed. The sanitized message part is the first non-empty line, so a message that starts with a newline still shows its text. The surfacing seam gets one event per digest: the first member (highest level, oldest) whose recorded result is `failed` or `unknown`. `digests` counts digests built and not released unsent; `sent`, `failed` and the other counts are member rows. After a digest no further call is made (it is the last step).

C-55: the retry schedule (#25), `retry.py`. `retry_schedule(kind, now)` returns `retry_at(attempts)`: `now` plus 60, 300, 1800 or 7200 seconds after attempt 1 to 4, and None from `attempt_cap(kind)` on (5; 3 for `wsl-notice`; an unknown kind gets 5). It is a pure function with no jitter, so it needs no seed and a digest, the claim of an escaped row and `apply_outcome` can all ask it. An `attempts` that is not an integer (a bool included) or is below 1, a non-integer `now` (a negative wall time is fine: `Lease` accepts any wall within the instant limit) and a non-string kind raise instead of answering, because a wrong answer would end a row `failed` or never retry it. The callers clamp a stored attempt count below 0 (corruption) to 0 before adding the call just made (`apply_outcome`, `record_digest`), so the schedule never sees less than 1 for a counted call and a recording never rolls back on it. `send.Seams.retry_schedule` defaults to it for `send` and `flush`. The step is counted from the end of the call (`lease.now` of the recording transaction), not clamped to the 24 hour expiry: the longest chain of steps is 9360 seconds, and a row that comes due after its 24 hours ends `expired` in `flush` step 4, attempts kept. A refusal retry (decision 5 of the handoff, the literal reading) takes the same step as any retry and counts an attempt. `lock_busy` and `env_missing` never ask the schedule: no attempt, no step, no cap.

C-56: `history` and `prune` (#26), `history.py`, `prune.py`. Choices where the interface is silent, all the narrower reading. `history`: every column is checked against the grammar of `schemas/cli/history.json` on its way out and a row that fails is left out with one warning (the database is a file anyone with write access to the state directory can edit); the connection decodes text with replacement so bytes that are not UTF-8 cannot fail the command; labels are matched with `json_each` inside a `CASE` on `json_valid`, one bound parameter each, and more than 16 distinct labels is an empty list without a query. `prune` takes one reading of the clock for every age cut-off, except that each queue batch builds its `Lease` inside its write transaction (a claim made after the first reading would otherwise look lapsed). It deletes in the order event ids, dedup windows, `surfaced`, counters, history, and ends the queue last: a dry run cannot expire anything, so counting a history row that the same run would free by expiring its queue row would make the dry run inexact, and a `surfaced` row that #27 inserts for an expired row would pin its delivery (the cost: those deliveries are history rows for the next run). `surfaced` rows go only when processed (a pending alert is never deleted, and it also pins its delivery) and when their period lies before the UTC day of now minus 2 days; a counter goes when its hour ended more than 2 days before now. Every batch is one `BEGIN IMMEDIATE` transaction of at most 1000 rows, a batch whose lock wait ran out is tried three times, and the run pauses 10 ms between batches so a waiting `send` gets the lock. A clock stepped back deletes less; one stepped forward ends old rows early (accepted: see Residual risks). With no config the default retentions (30 days, 14 days) apply and the lease is the longest there is (the most claims read as live). An expiry batch ends at most 1000 queue rows; each row has its own `deliveries` update and its own release of dedup records, in the same transaction. The dedup windows and event ids that this release deletes are counted under `queue`, not under `dedup` or `event_ids` (a recorded judgment call: those two count what their own age rules delete, and the dry run and the run give the same numbers). A batch that stays busy is tried three times (each try waits the 5 s busy timeout), so a busy database ends the run after about 15 s; the message for it is `state database is busy` (a fixed text, no value echoed). The `+s.processed` in the eligibility predicate keeps SQLite from scanning the whole pending index once per candidate row (30000 pinned rows took 135 s in one transaction). The expiry select decodes text with replacement and a row whose source, destination or level is outside the grammar of the log is expired without a log line (the schema requires all three; a line that cannot be built is a log problem, never an exception, and `prune` warns once). A `history` limit is applied in SQL before the row check, so skipped rows use places of the limit. An empty `state.db` is no database for `prune` too (it asks the read-only open first; an older schema still migrates). Expired rows are given to `Seams.surface` only for a destination that is configured and enabled (done in C-57), and logged as `delivery` lines when the config keeps a log.

C-57: surfacing, failure alerts and the `post-fail` hook (#27), `surfacing.py`, `alerts.py`, `hooks.py`. Choices where the interface is silent, all the narrower reading. Surfacing is keyed on the recorded outcome, never on a notifier's code alone: a `failed` or `unknown` result whose code is one of the four hourly words or absent is surfaced as `other` (a notifier cannot use up an hourly slot), and the 9th distinct daily code of a destination and day becomes `other` (the row `other` itself is not one of the 8). `Seams.surface` gets `SurfaceEvent.now` (the recording transaction's clock) and is the default `send.surface_event`; evictions (`dropped`/`overflow`) are surfaced from `send`, `flush`, digests, releases of claims and the decision, `expired` from `flush` step 4 and `prune`, `env_missing` by `flush` when it skips a destination for an unset variable (only when the destination has an unclaimed due queue row, one that is no alert when there is one: an idle destination without its credential, or one whose rows are held or claimed, is not a failure; `send`'s `env_missing` deferral surfaces nothing, `flush` does it at its next run). The row cited for `expired` and `overflow` is likewise the first one that is not a failure alert (an alert row would only run the hooks and spend the hour's slot), and an escaped call (`unknown`/`killed`) like any `unknown`. `flush` takes the pending `surfaced` rows before it starts the destinations, one `BEGIN IMMEDIATE` transaction per row (at most 1000 per run): it reads the delivery, sets `processed = 1` and routes the alert in that transaction, so two flushers take a row once and `prune` cannot delete the delivery between the read and the mark; a dry run and a disabled or unconfigured router take nothing. A row whose delivery is gone, whose destination is removed from the config, or whose columns fail the payload grammar is processed and skipped (no alert, no hook); a destination disabled since still routes the alert and runs the hook (round 1: only `expired` is restricted to enabled destinations, at surfacing). A `StoreError` part way returns the jobs and log lines of the rows already committed (`Taken.error`), so their hooks run; any other exception in the routing of one row rolls its alert back, marks the row processed in a transaction of its own and keeps its hook job, so a faulty row cannot block every later flush. The alert is `decide.decide_alert`: steps 1 to 6 of `send`, then an unclaimed `single` row due now with outcome `deferred` and no reason (the closed history reasons have none for it); the destination's step 6 claims it, so the cap and the credential check happen there and the same run delivers it. A rule that does not route the alert (`no_rule`, `drop`) writes a log line and the destination-less `deliveries` row `send` writes for those cases (source `notice-route`, hook `post-fail`, outcome `dropped`, reason `no_rule`/`rule_drop`; never surfaced, pruned like any history row). An alert row is never `held` by the cap, so no `rate_capped` deferral exists for it; its cap is the hooks-only handling of any surfaced row whose source is `notice-route`. A surfaced row whose failing notification has source `notice-route` runs the hooks and routes nothing. The hook payload's `outcome` for the hourly codes follows the code (`deferred`, `dropped`, `expired`), otherwise the delivery's own (`failed` or `unknown`). Hooks run through `Gateway.run` (`sh -c`, own session and group, `PATH`/`LANG`/`LC_ALL` as for a notifier plus the three `NOTICE_ROUTE_*` variables, payload on stdin as one ASCII JSON line, output capped and dropped); synchronous hooks run on at most four threads while the destinations work and `flush` waits for them (once a signal is trapped no further one is started: the unstarted ones are started detached, a running one finishes within its timeout); an `async` hook is started by `Gateway.run_detached` after everything else (a double fork whose supervisor has the default signal dispositions and no descriptor beyond 0 to 2, whatever its number, so it holds no flush lock; the parent reports `spawn_failed` unless the first child exited 0, and a SIGKILLed supervisor or flush leaves the hook without a timeout, inherent) and nobody waits for it. A hook failure of any cause (an OS fault is `lost`) is one fixed-word warning on stderr (`a post-fail hook failed (timeout)`) and changes neither the exit code nor the document, and every run of a hook is a `hook` record in the log (`mode` `sync` with the observed `result`, or `async` with `started`/`spawn_failed` only: the supervisor's later result is not observed; the record carries no output). The TERM grace after a hook's timeout is 5 s before KILL. The delivery log line of an alert's flush call carries no `hook` (flush log lines never do). A fault of the routing of one row (not of the database) is counted and `flush` adds exactly one fixed-word warning (`a failure alert could not be routed`, no exception text) without changing the exit code. A sync hook that a signal kept from starting is started detached and logged as mode `sync`, result `started`.

Choices where the interface is silent, all the narrower reading. `crontab` is found only on the cleaned `PATH` of the gateway's environment (a relative or unsafe entry never counts, and there is no fallback list) and started by its absolute path with the environment `PATH` and `LC_ALL=C` and nothing else, so `NOTICE_ROUTE_HOOK` never reaches it or the block; the call has a 30 s deadline and the gateway's output caps, so a crontab above 64 KiB is unreadable (exit 1, never written). The cron lines are exactly `flush --quiet` and `prune --quiet` (no `--actor`: `flush` falls back to `auto:unknown` off a terminal); a block line above 999 bytes is refused. Output: the action word (plus the words dry run in parentheses) and, for `install` that changes something, the block, on stdout, nothing under `--quiet`; `--json` is the schema document. `uninstall` removes a block of any version and reports it with trailing spaces, tabs and carriage returns removed from each line (so a CRLF block is shown with LF), and non-UTF-8 bytes shown as U+FFFD; the `block` of its schema matches any `# notice-route managed v...` header. The crontab is read twice and written once with no lock: a change made between the second read and the write is not detected (the last writer wins). Nothing is logged and no state directory is created. The suite runs under an autouse guard (`tests/crontab_guard.py`) that refuses any `crontab` that is not the per-test fake, by name and by `realpath`, in this interpreter only (it covers `Popen`, `os.exec*`, `os.spawn*`, `os.posix_spawn*`, shell command words and interpreter arguments; `os.system` is refused outright; a child process, `ctypes` and a copied binary are not covered).

## Queue and row model

Every notification a destination will receive later is one queue row of kind `held` (quiet hours or the cap; folded into a digest) or `single` (everything else; always sent as itself). A row is claimed by the transaction that decides to call it, in `send` and in `flush` alike, and every result is recorded only on the row the recorder still holds. The 100-row cap counts unclaimed rows only and is applied by every transaction that leaves a row unclaimed. Event-id and repeat records live exactly as long as their delivery is pending, `sent` or `unknown`. Surfacing only writes a `surfaced` row; the next `flush` routes the alert and runs the `post-fail` hooks, so `send` never runs a hook and its time bound holds. `flush` writes a heartbeat that `validate` and `send` read, so a dead cron is visible. The rules are in [Deferral and digest](interface.md#deferral-and-digest), [Dedup](interface.md#dedup), [Retries and outcomes](interface.md#retries-and-outcomes) and [Hooks](interface.md#hooks).

## Concurrency

Any number of `send` and `flush` processes may run at once. The decision step is one `BEGIN IMMEDIATE` transaction with a 0.5 second busy timeout in `send` (two transactions, the 1 s of the time bound) and 5 seconds elsewhere; `prune` deletes in batches of 1000. It also writes the queue rows of the destinations to be sent now. The send step is serialized per destination by `flock`, and all `wsl-notice` destinations share `locks/_wsl.lock`. Every call claims its rows (a lease of twice `send_worst_case_s`), and a result is recorded only on rows the recorder still holds; `flush` resends a row whose claim expired. A `flush` holds a per-destination flush lock for its whole run, and per call the send lock and a claim. Every full `flush` records its start in `meta.flush_last`; `validate` and `send` read it to report a stopped cron. Deviation from design guide section 4.3: per-destination locks are kernel `flock`s, not leases in `state.db`; the kernel releases them when the holder dies, which is the property a lease provides. Queue rows carry leases (claims). Exact PIDs the router started are the only processes it signals, as process groups it created.

## Error handling

Failures are values: every call ends in one of the outcomes of [Retries and outcomes](interface.md#retries-and-outcomes), recorded in `history` and `log.jsonl`. State problems fail closed as [Files](interface.md#files) says: nothing is sent when the database cannot be used. Config errors fail fast with the key named and never the value.

## Test strategy

- Every subprocess, lock and clock use goes through `gateway.py`; tests substitute fakes. Fake notifiers live in `tests/fakebin/` and can exit with any code, print any envelope, sleep, ignore SIGTERM, spawn a grandchild, close stdin early and write oversized output.
- `--json` outputs have golden files and are validated against `schemas/`; the sibling notifiers' error envelope and `send` schemas, with their `defs.json` and `notification.json`, are copied into `tests/` at a pinned version.
- Process tests run in CI: group kill with a grandchild, the bounded reader, `flock` serialization across 8 processes including a SIGKILLed holder, concurrent `send` and `flush` claiming each row once, SIGKILL after the decision transaction and before the call (the row is sent by the next `flush` and a redelivery of the same `event_id` is `redelivered`), SIGTERM before the call (claims cleared, exit 128+N), two `flush` on one destination with 40 due rows (each row sent once), the dedup statement under 8 writers.
- Spike regressions: the window brute force as a property test; the strict reader cases; the template non-re-expansion case; bad time zone keys; the fixture "New York, 2026-11-01, window 22:00 to 01:30: inside until 01:30 EDT, inside again 01:00 to 01:30 EST".
- Behavior cases: a `failed` first send, then the next identical notification inside the window is sent; agent-spawn and claude-session both send `event_id: 41` to one destination, and both are sent; an evicted (`overflow`) and an `expired` row: the producer's redelivery of the same event is sent; a release after a later window opened with the same key leaves the later window.
- Queue and flush cases: a `send` stalled past its lease (SIGSTOP), `flush` resends and records `sent`, the stalled `send` resumes: `sent` stays; `prune` and an overflow eviction during a `flush` call leave the claimed rows alone; a quiet destination with one due `error` and ten `warn` rows: the `error` is sent, state `done`, the `warn` rows get the window's end; an `info` held for the cap and due in quiet: `dropped`, `quiet`; every destination `already_running`: exit 0; SIGTERM during a `flush` call; a config with no `flush` for 6 minutes: `validate` warns `flush_stale`, and an `env_missing` send prints the advisory line.
- Outcome table: one case per row, plus exit 0 with oversized stdout (row 3), exit 20 with garbage stdout (row 9), `generic` exit 22 (row 6), SIGKILL from outside (row 4), exit 143 (row 18).
- Database timing: a `prune` of 100000 rows and 8 concurrent `send`s: no `send` waits more than 0.5 s per transaction; the record transaction fails after a call: exit 1, the row is resent by `flush` once.
